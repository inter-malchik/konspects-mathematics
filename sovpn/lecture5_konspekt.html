§1. Связь нескольких GPU (сл. 3–9)

1.1. Зачем нужны коммуникации? (сл. 3)

Обучение на одном GPU упирается в два ограничения: по памяти — нужно хранить параметры, градиенты, состояния оптимизатора и активации — и по скорости вычислений (сл. 3). Масштаб иллюстрируется расчётом: предобучению современной модели требуется порядка $4.8\cdot10^{26}$ FLOPs; на одной H100 в типе fp16 на пиковой мощности это заняло бы $\approx 7600$ лет (сл. 3).

Из записи лекции [01:03–02:30]

Лектор поясняет источник числа шуткой: даже если бы удалось разместить гипотетическую модель на 700 млрд параметров целиком на одной видеокарте («перепаяли чипы на суперкрутые, каких даже в природе нет»), обучение всё равно упёрлось бы в скорость вычислений — отсюда оценка «~7600 лет» на пике FP16 одной H100. Вывод: нужно наращивать не мощность одной карты, а их число. Для моделей на триллионы параметров нужны кластеры не на десятки тысяч, а на сотни тысяч GPU; в качестве примера того, что такие кластеры реально строят и заставляют работать, лектор упоминает Colossus у xAI на 200 000 GPU.

Вне слайдов

Оценка «~7600 лет» проверена в песочнице. По официальным спецификациям NVIDIA пиковая производительность H100 SXM в FP16/BF16 составляет 989 TFLOPS без структурной разреженности (dense) и 1979 TFLOPS со структурной 2:4-разреженностью (sparsity). При $4.8\cdot10^{26}$ FLOPs и пике 1979 TFLOPS получаем $\approx 7686$ лет — практически совпадает со слайдом. На плотной (dense) арифметике, ближе к реальному предобучению без специальной разрежённости весов, время вдвое больше — $\approx 15\,373$ лет. Слайд не уточняет, какая именно цифра H100 использована; на защите стоит иметь в виду, что «~7600 лет» — это оценка именно по пиковой производительности «с разреженностью», а не по типичной для плотных матричных умножений при предобучении.

1.2. Устройство GPU-ноды (сл. 4)

Нода — базовая единица объединения GPU: небольшой сервер, в котором обычно установлено 8 GPU, один или несколько CPU-сокетов, оперативная память хоста, PCIe-мост и сетевые карты (сл. 4).

Рисунок (сл. 4). «Устройство GPU-ноды». Две ноды (Node 0, Node 1), в каждой — GPU с несколькими SM (потоковыми мультипроцессорами) и GPU-памятью, буферы sendBuff/recvBuff, DMA-движок, шина PCIe, Proxy Thread и Host Memory на CPU-стороне, сетевая карта (NIC). Между нодами подписаны два типа связи: IB (InfiniBand) и Socket.
Из записи лекции [02:30–05:42]

CPU в ноде оркестрирует запуск вычислительных и коммуникационных ядер; память хоста (RAM) хранит данные и при острой нехватке видеопамяти может использоваться для CPU-offloading — выгрузки части весов/градиентов/активаций из GPU в RAM (лектор подчёркивает: это крайняя мера). Отдельно упомянута архитектура GB200 (Grace + Blackwell): в одной ноде может быть до 16 GPU-чипов, но это не 16 «полноценных» видеокарт — GB200 объединяет два GPU-чипа с одним CPU-чипом («Грейс» — CPU, «Блэквелл» — GPU) в одном модуле.

На пальцах

Ноду удобно представлять как «общежитие» для GPU: у каждого GPU — своя комната (память), но общий вход (PCIe-шина) и вахтёр на входе (CPU), который решает, кому когда пользоваться общим коридором.

1.3. Внутринодовая связь GPU (сл. 5–6)

Базовый способ связи GPU внутри ноды — шина PCIe (медленно, но универсально: через неё же GPU общается с CPU, памятью хоста и сетевой картой). Более продвинутый способ — NVLink (быстро), подключаемый отдельно от PCIe и соединяющий GPU попарно (сл. 5). Формат «все со всеми» через NVLink требует слишком много прямых соединений; чтобы его избежать, используется коммутатор NVSwitch (сл. 6).

Рисунок (сл. 5). «Внутринодовая связь GPU». Два CPU сверху, каждый подключён к двум PCIe-коммутаторам; под ними — 8 GPU (P100), связанных между собой сплошными линиями NVLink и пунктирными PCIe, часть связей — крест-накрест.
Рисунок (сл. 6). «Внутринодовая связь GPU». Два варианта на 8 GPU: сверху — конфигурация без NVSwitch (каждый GPU соединён линиями напрямую сразу с несколькими другими — густая сеть пересекающихся связей); снизу — конфигурация с NVSwitch (все GPU подключены к одному общему коммутатору NVSwitch, связи не пересекаются).

Дополнительно к тому, что на слайде: важна NUMA-локальность. Обычно в ноде два CPU-сокета, и каждый «отвечает» за свои 4 GPU; желательно, чтобы GPU обменивался данными с памятью хоста и NIC именно «своего» сокета, а не соседнего — иначе такая группа из 4 GPU перестаёт быть NUMA-однородной. Про формат NVLink «все со всеми»: лектор сам себя поправляет по ходу объяснения рисунка — он сначала сказал, что показанная схема и есть «все со всеми», но затем уточнил, что это не так: например, GPU в верхнем левом углу схемы не связан напрямую с GPU в правом нижнем углу, и данным между ними приходится идти транзитом через промежуточный GPU по имеющимся линиям NVLink. Уточнение (08:01). Именно эта неполнота прямых связей и есть причина, по которой нужен NVSwitch — он избавляет от необходимости тянуть NVLink-провод от каждого GPU к каждому.

Вне слайдов

Отдельное важное свойство, которое лектор упоминает при обсуждении межнодовой связи, но которое в равной мере относится и к внутринодовой: связь P2P (peer-to-peer) позволяет GPU читать данные из памяти другого GPU напрямую (GPU0 → GPU1), тогда как без неё данные идут через CPU RAM (GPU0 → CPU → GPU1), что заметно дороже (communications.pdf, §1.2).

1.4. Межнодовая связь GPU (сл. 7)

Ноды объединяются в кластер через сеть — обычно Ethernet или InfiniBand — посредством сетевых карт (NIC) внутри каждой ноды (сл. 7).

Иерархическая сеть: наверху облако «Public Network», под ним «Border Leaf», ниже — уровень «Front End Spine Switch» (2 коммутатора), ещё ниже — четыре «Front End Leaf Switch»/«Front End Leaf», а внизу — три группы по 8 GPU с CPU и NIC, объединённые общей шиной «GPU Fabric».

Кратко: для выхода за пределы одной ноды (до тысяч и десятков тысяч нод) нужна именно такая многоуровневая сетевая структура, а не прямые связи каждой ноды с каждой.

Вне слайдов

По письменному конспекту лектора (communications.pdf, §1.3): наивная схема межнодовой связи выглядит как GPU0 → CPU0 memory → NIC0 → сеть → NIC1 → CPU1 memory → GPU1 — с проходом через память CPU на обеих сторонах, что дорого. Чтобы этого избежать, используется RDMA (remote direct memory access): данные идут напрямую от GPU к NIC, минуя CPU-память, — GPU0 → NIC0 → сеть → NIC1 → GPU1. Для передачи данных по сети при обучении LLM обычно используется InfiniBand.

1.5. Топология кластера (сл. 8)

Соединять тысячи нод «все со всеми» слишком дорого, поэтому используются специальные топологии: fat-tree (толстое дерево, на картинке), dragonfly, torus (сл. 8).

Рисунок (сл. 8). «Топология кластера». Схема fat-tree: несколько уровней узлов-квадратов, соединённых линиями с перекрёстными связями (крест-накрест между соседними парами на каждом уровне), внизу — конечные узлы (кружки), сгруппированные пучками под нижним уровнем дерева.
Из записи лекции [10:24–13:55]

Идея fat-tree: чем выше уровень дерева, тем больше связей (пропускной способности) — так компенсируется возросшая задержка при подъёме наверх. Пример: паре GPU, соединённых через один общий коммутатор, требуется два шага (узел→коммутатор→узел). Если нужным узлам приходится подниматься на третий уровень дерева, у данных появляется несколько возможных маршрутов вниз — и на этом уровне пропускная способность вырастает вдвое по сравнению с нижним уровнем, что как раз компенсирует дополнительные шаги. Dragonfly: небольшие группы нод в формате «все со всеми» объединяются в иерархию поверх этих групп. Torus (1D/2D/3D): ноды соединены в кольцо (нода 1 → нода 2 → … → последняя нода → нода 1); 2D-torus добавляет такое же кольцевое соединение «по строкам» между несколькими такими кольцами, 3D — ещё одно измерение колец.

1.6. Стоимость коммуникаций (сл. 9)

Основные метрики стоимости коммуникации — задержка передачи $\alpha$ и пропускная способность $B$. Общая модель стоимости коммуникации объёма $n$: $$T_{\text{comm}}(n) \approx \alpha + \frac{n}{B}.$$ Вывод: много мелких пересылок — плохо (упор в задержку, лучше объединять в пакеты побольше); слишком большие пакеты — упор в пропускную способность (сл. 9).

Из записи лекции [13:55–18:58]

Лектор связывает формулу с топологией: чем дальше друг от друга находятся ноды (например, наверху fat-tree), тем сильнее сказывается задержка $\alpha$. Практический вывод сформулирован явно: если разрабатываемый механизм обучения пересылает огромное число мелких пакетов, их стоит объединять в более крупные — иначе упор в задержку передачи; если же пакеты и так большие, упираются уже в саму пропускную способность сети, и её нужно так или иначе увеличивать.

§2. Коммуникации (сл. 11–23)

2.1. Point-to-point коммуникации (сл. 11)

Простейший вид обмена данными между двумя GPU: send (отправка данных из буфера) и receive (приём в буфер) (сл. 11).

Данные отправляются в формате небольших буферов: на GPU-0 нужный кусок копируется в отдельный раздел памяти, на GPU-1 при выполнении receive тоже выделяется буфер приёма; GPU-1 ждёт данные от GPU-0, принимает их и затем копирует из буфера в основную память. Именно поэтому реальные системы предпочитают point-to-point не напрямую, а через паттерны с заранее фиксированным порядком действий — коллективные коммуникации.

2.2. Коллективные коммуникации (сл. 12–17)

В коллективных коммуникациях участвует не пара, а целая группа рангов (процесс-группа). Шесть базовых операций (сл. 12–17), каждая как результат редукции или перераспределения тензоров по 4 рангам:

  • AllReduce (сл. 12) — все ранги получают результат редукции (например, суммы) данных со всех рангов: $\text{out}[i]=\sum_X \text{in}_X[i]$.
  • Broadcast (сл. 13) — тензор с одного (корневого) ранга копируется на все остальные: $\text{out}[i]=\text{in}[i]$.
  • AllGather (сл. 14) — каждый ранг хранит свой кусок тензора, в результате все ранги получают полный, собранный из всех кусков тензор: $\text{out}[Y{\cdot}\text{count}+i]=\text{in}_Y[i]$.
  • Reduce (сл. 15) — то же, что AllReduce, но результат помещается только на один (корневой) ранг: $\text{out}[i]=\sum_X \text{in}_X[i]$ (только на корне).
  • ReduceScatter (сл. 16) — редукция и разбиение результата за одну операцию: $\text{out}_Y[i]=\sum_X \text{in}_X[Y{\cdot}\text{count}+i]$, каждый ранг получает только свою часть.
  • AllToAll (сл. 17) — самая дорогая операция: каждый ранг отправляет разные части своего тензора всем остальным рангам: $\text{out}_X[Y{\cdot}\text{count}+i]=\text{in}_Y[X{\cdot}\text{count}+i]$.
Рисунки (сл. 12–17). Единый визуальный формат для всех шести операций: 4 цветных прямоугольника rank 0–3 слева (входные данные, окрашены по рангу), стрелка, 4 прямоугольника справа (результат); в Broadcast/Reduce только один ранг помечен «(root)»; в AllGather/ReduceScatter/AllToAll итоговые прямоугольники разбиты на цветные полосы, показывающие, из чьих кусков собран результат.

На пальцах

Оба пути математически эквивалентны AllReduce, но выполнение их как одной слитной операции дешевле, чем как двух последовательных.

2.3. NCCL: модель исполнения (сл. 18)

Коммуникатор задаёт группу рангов; ранги бывают локальными (внутри ноды) и глобальными. Коммуникации обычно располагаются в отдельном (соседнем с вычислительным) стриме для асинхронного выполнения (сл. 18).

2.5. NCCL: протоколы передачи данных (сл. 20)

Три протокола передачи с разным балансом «пропускная способность / задержка»: Simple, LL (Low Latency), LL128 (сл. 20).

Из записи лекции [33:16–37:29]

Simple использует барьеры памяти (memory fences) для гарантии порядка и видимости данных — высокая пропускная способность, но и высокая задержка синхронизации. LL отказывается от барьеров: на каждые 4 байта полезных данных передаётся ещё 4 байта флага, подтверждающего, что данные валидны и можно их читать; задержка ниже, но полезная пропускная способность падает вдвое (данные и служебный флаг — поровну). 2.6. NCCL: алгоритмы коммуникации — кольцо, дерево, иерархический (сл. 21–23)

Одну и ту же коллективную операцию можно выполнить разными алгоритмами обмена данными: Ring (кольцо), Tree (дерево), иерархический (сл. 21–23).

Рисунок (сл. 22). «NCCL. Алгоритм "дерево"». Последовательность Reduce (снизу вверх к корню GPU0) и Broadcast (сверху вниз); отдельно — схема «Tree Topology»: GPU0 (Root) — GPU2 (Middle) — GPU1 и GPU3 (Leaf).
Из записи лекции [37:29–42:03]

Ring: каждый ранг одновременно передаёт данные следующему и принимает от предыдущего; для операции редукции это удобно и заметно снижает задержку по сравнению с последовательным обходом. Проблема — число шагов растёт линейно с числом рангов $O(N)$: для 1000 GPU потребуется порядка 1000 таких пересылок, что уже дорого. Tree снижает сложность до $O(\log N)$ (для 1000 рангов — порядка $3\log_2 10\approx 10$ шагов, по словам лектора «не так уж неприятно»), но за это платится тем, что GPU у корня дерева получают больше данных, чем остальные — возникают «бутылочные горлышки». Иерархический алгоритм сочетает оба: внутри ноды, где связь быстрая, используется кольцо; между нодами, где связь заметно медленнее (и число нод может доходить до тысячи, для которых кольцо уже не годится), — дерево (сл. 23).

§3. Параллелизм данных (DP) (сл. 25–28)

3.1. Распределённый параллелизм данных (DDP) (сл. 25)

Батч делится между GPU; параметры реплицируются на каждом ранге. На ранге $i$ считается локальный лосс $\mathcal{L}_i^{(t)}=\mathcal{L}_{w_t}(B_i)$ по своей части батча $B_i$; поскольку активации и данные разные, градиенты $g_i^{(t)}=\nabla_{w_t}\mathcal{L}_i^{(t)}$ на разных рангах тоже разные, а веса должны остаться одинаковыми — поэтому градиенты усредняются через AllReduce: $g^{(t)}=\frac1N\sum_{j=1}^N g_j^{(t)}$ (сл. 25).

Рисунок (сл. 25). «Распределённый параллелизм данных (DDP)». Две ноды с одинаковой моделью (одни и те же веса загружены на оба GPU), разные подбатчи входа; на каждой — цепочка FWD1→FWD2→FWD3→Loss→BWD3→BWD2→BWD1→градиенты $w_1,w_2,w_3$.grad; между нодами подписано «minibatch split in half», справа — разные выходы/target для каждой ноды.

Решение — усреднить градиенты через AllReduce.

Указание к ЛР / инженерная деталь (48:50–51:55). Наивно ждать полного backward перед AllReduce — то есть терять возможность спрятать коммуникацию под вычисления. Поэтому на практике применяется bucketing: как только градиенты очередного слоя (или нескольких слоёв, объединённых в «бакет») готовы, для них сразу запускается AllReduce, параллельно с вычислением backward для следующего слоя. Компромисс размера бакета: бакеты покрупнее лучше утилизируют пропускную способность сети, но последняя коммуникация в конце всё равно не успевает спрятаться под вычисления — поэтому размер бакета выбирается сбалансированно (для больших слоёв — бакеты покрупнее, для маленьких — помельче).

На пальцах

DDP с усреднением градиентов — как несколько бухгалтеров, каждый обсчитывает свою пачку чеков независимо, а в конце дня все сверяют итоги и берут среднее, чтобы у всех в отчёте была одна и та же цифра. Bucketing — не ждать, пока обсчитают всю пачку целиком, а сверяться по частям, по мере готовности каждой связки чеков.

3.2. ZeRO-1 и ZeRO-2 (сл. 26–27)

DDP реплицирует параметры, градиенты и состояние оптимизатора целиком на каждом ранге — избыточно с точки зрения памяти. ZeRO (Zero Redundancy Optimizer) вместо этого шардирует их между рангами. ZeRO-0 — это и есть обычный DDP (полная репликация). ZeRO-1 ($P_{os}$) шардирует только состояние оптимизатора: каждый ранг хранит и обновляет лишь свою часть, после чего актуальные параметры собираются заново через AllGather (сл. 26). ZeRO-2 ($P_{os+g}$) дополнительно шардирует градиенты: $g_i^{(t)}=[g_{i1}^{(t)},g_{i2}^{(t)},\dots,g_{iN}^{(t)}]$, каждый ранг хранит только свой шард $g_{ii}^{(t)}$; вместо AllReduce используется ReduceScatter, после которого ранг $i$ получает и суммирует именно свою часть: $g_i^{(t)}=\frac1N\sum_{j=1}^N g_{ij}^{(t)}$ (сл. 27).

§4. Тензорный параллелизм (TP) (сл. 30–35)

4.1. Параллелизм по столбцам и по строкам (сл. 30–31)

Тензорный параллелизм использует два свойства матричного умножения. Первое — разбиение по столбцам: $A\cdot B=A\cdot[B_1\ B_2\ \cdots]=[A\cdot B_1\ \ A\cdot B_2\ \cdots]$; для линейного слоя $Y_i=XW_i$ — матрица весов делится по столбцам, каждый ранг считает свою часть выхода (сл. 30). Второе — разбиение по строкам: $A\cdot B=[A_1\ A_2\ \cdots]\cdot\begin{bmatrix}B_1\\B_2\\\cdots\end{bmatrix}=\sum_i A_iB_i$; входы делятся по столбцам, веса — по строкам, частичные результаты складываются (сл. 31).

Рисунок (сл. 31). «Параллелизм по строкам». X разбит по столбцам (scatter) на $X_0$/$X_1$ (4,1) каждый; $W_0$/$W_1$ (1,2) — разные строки весов; частичные $Y_0$,$Y_1$ (4,2) объединяются через all_reduce (суммируются) в итоговый Y (4,2).
Из записи лекции [01:03:37–01:06:57]

Плюс параллелизма по столбцам — ускорение вычисления одного слоя (тяжёлая по FLOPs операция матричного умножения делится на несколько GPU) и уменьшение памяти на веса, но копируются (дублируются) входные активации — а раз FSDP и так уже умеет шардировать параметры, выигрыш по памяти именно от шардирования весов в TP уже не так существен. Параллелизм по строкам решает именно проблему активаций: каждый девайс хранит лишь часть активаций, а не полную копию, — но платит за это тяжёлым AllReduce после каждого слоя.

4.2. TP в FFN-блоке (сл. 32)

В FFN-блоке два линейных слоя. Для первого применяется параллелизм по столбцам, для второго — по строкам: тогда промежуточный AllGather/ReduceScatter между ними не нужен — единственная коммуникация всего блока сливается в один AllReduce в конце (сл. 32).

А вот вторая матрица каждого устройства, показанная на схеме как «$Y2_k$», на самом деле численно равна не $Y1_k\cdot W2_k$ (как подсказывают стрелки диаграммы, идущие от $Y1_k$), а произведению k-го столбца исходной матрицы $X$ на $W2_k$: $Y2_0 = X[:,0{:}1]\cdot W2_0$, $Y2_1 = X[:,1{:}2]\cdot W2_1$. Итоговая сумма $Y2=Y2_0+Y2_1$ (результат all_reduce) при этом совпадает со слайдом, и сама идея блока (частичные произведения складываются через AllReduce) неверной от этого не становится — только конкретная иллюстрация того, как получены промежуточные $Y2_0/Y2_1$, не выстраивается в цепочку из $Y1_0/Y1_1$, как предполагают стрелки на рисунке. Рисунок взят из «Ultra-Scale Playbook» (Hugging Face) — расхождение, по всей видимости, в исходном материале, а не привнесено при переносе на слайд.

4.4. Параллелизм последовательностей (SP) (сл. 35)

Между блоками TP остаются Dropout и LayerNorm — операции, которые плохо параллелятся тем же способом (по столбцам/строкам матрицы весов). Параллелизм последовательностей (SP) решает это, разделяя саму последовательность (а не матрицу весов) между устройствами для этих промежуточных операций, и объединяется с TP в единый пайплайн (сл. 35).

§5. Контекстный параллелизм (CP) (сл. 37–39)

5.1. Кольцевое внимание (Ring Attention) (сл. 37–38)

При очень длинном контексте (порядка миллиона токенов) хранить все активации внимания на одном GPU тяжело: вычисления растут квадратично, а память — линейно, но с огромным множителем. Контекстный параллелизм (CP) делит сам входной контекст между рангами; чтобы внимание всё равно считалось по всей последовательности, K/V-блоки передаются по кольцу между GPU — это и есть Ring Attention (сл. 37).

Рисунок (сл. 37). «Кольцевое внимание (Ring Attention)». 4 GPU в кольце (GPU1↔GPU2↔GPU3↔GPU4↔GPU1), у каждого — своя тройка $Q_i,K_i,V_i$.
Рисунок (сл. 38). «Кольцевое внимание (Ring Attention)». Дополнительно справа — «Causal Attention Mask»: таблица 16×16 (Token Index), раскрашенная по 4 GPU по диагональным блокам-«лесенкам» (GPU 1 — маленький треугольник в углу, GPU 4 — самая широкая полоса).
Из записи лекции [01:21:15–01:26:11]

По сути кольцевого внимания: каждый ранг хранит свой блок запросов $Q_i$ и на каждом шаге кольца получает очередной блок $(K_j,V_j)$ от соседа; вычисление похоже на алгоритм Ring из NCCL. Проблема видна на маске: GPU 1 (в примере на 16 токенов) реально вычисляет только один блок, а GPU 4 — все четыре, то есть нагрузка между рангами не сбалансирована — время работы всего контекстного внимания определяется самым загруженным GPU.

5.2. Zig-Zag Ring Attention (сл. 39)

Чтобы выровнять нагрузку, применяется более умная нарезка последовательности между рангами — Zig-Zag Ring Attention (сл. 39).

Рисунок (сл. 39). «Zig-Zag Ring Attention». Та же причинная маска 16×16, но раскраска по GPU теперь «зигзагом»: каждому GPU достаются два непримыкающих по индексу диагональных фрагмента маски (например, GPU 1 — блоки токенов 1–2 и 15–16), так что суммарно закрашенная площадь на каждый GPU почти одинакова.

§6. Конвейерный параллелизм (PP) (сл. 41–43)

Мотивация PP (звучит в записи между слайдом-разделителем и сл. 41, специального слайда под неё в колоде нет): у TP есть потолок в 8 GPU (внутри ноды), а у CP — свой потолок из-за растущего числа пересылок по кольцу; даже вместе с FSDP (только на ZeRO-1, иначе коммуникаций становится слишком много) этого недостаточно для кластеров на тысячи GPU — нужна ещё одна, более «крупнозернистая» ось параллелизма, режущая модель по слоям, а не по тензорам.

6.1. AFAB (сл. 41)

Модель делится по слоям на стадии конвейера ($P$ рангов): $f(x)=s_P(s_{P-1}(\ldots s_1(x)))$, каждая стадия хранит только свои слои целиком. Простейшее расписание — AFAB (All-Forward-All-Backward): сначала forward для всех стадий, затем backward в обратном порядке (сл. 41).

Рисунок (сл. 41). «AFAB». Диаграмма GPU 1–4 × время: на каждом GPU сначала блок Forward pass (номера микробатчей 1–16, ступенчато сдвинутые по времени между GPU), затем большой промежуток Device idle, затем блок Backward pass (в обратном порядке номеров).
Из записи лекции [01:36:05–01:38:05]

Механика: первая стадия получает входной микробатч, считает свою часть модели и передаёт активации следующей стадии через point-to-point send/recv; так по очереди все стадии выполняют forward, затем в обратном порядке — backward (обычно вдвое дольше forward). Главная проблема AFAB — очень большой простой рангов (device idle): пока не готовы данные, GPU просто ждут, что лектор называет «непозволительной роскошью».

На пальцах

AFAB — это конвейер, где вся бригада сначала собирает изделия от начала до конца партии, а уже потом та же бригада, в обратном порядке, всё разбирает и проверяет: пока разбирают одно звено, остальные стоят без дела. 1F1B — тот же конвейер, но разборка начинается сразу за первым же готовым изделием, не дожидаясь конца всей партии.

6.2. 1F1B (сл. 42)

1F1B (One-Forward-One-Backward) начинает backward, не дожидаясь, пока все стадии закончат forward — заметно сокращает простой (сл. 42).

Рисунок (сл. 42). «1F1B». Та же диаграмма GPU×время, но forward- и backward-блоки чередуются гораздо плотнее, промежутки device idle значительно короче, чем на схеме AFAB.
Из записи лекции [01:38:05–01:41:04]

Идея заимствована из параллелизма данных: батч уже разбит на микробатчи (например, 128 объектов → 32 ранга по 4 объекта); вместо ожидания форварда по всем объектам сразу, каждый ранг, посчитав активации по одному микрообъекту, тут же начинает пересылать их дальше и параллельно считает следующий микрообъект. Аналогично для backward — не нужно ждать окончания прямого прохода по всем объектам, чтобы начать считать градиенты по уже готовым. Итог — заметно меньший простой, но заметно более сложное для понимания и реализации расписание.

§7. 5D параллелизм (сл. 45–50)

7.1. Иерархия параллелизмов: TP → CP → SP → EP → PP → DP (сл. 45–50)

Слайд «Собираем все параллелизмы вместе» раскрывается лектором пошагово, добавляя по одной оси за раз (сл. 45–50): (1) TP — строго внутри ноды, TP≤8; (2) CP — желательно тоже внутри ноды, но «часто CP·TP>8»; (3) SP=TP·CP, чтобы GPU не простаивали в ожидании своей операции; (4) EP (экспертный параллелизм) — для MoE-блоков вместо FFN, тема следующих занятий; (5) PP — для масштабирования поверх TP/CP/SP/EP уже на медленной межнодовой связи; (6) DP — только с шардированием ZeRO-1, поверх всех остальных видов параллелизма.

Бывают локальные (внутри ноды) и глобальные ранги.Как «место за столом» в групповой коммуникации — обычно один GPU занимает одно место, но иногда несколько мест логически относятся к одному физическому устройству.
Коммуникатor (сл. 18)Программная (не аппаратная) сущность, задающая группу рангов, которая выполняет коммуникационные операции друг с другом.Список приглашённых на конкретный созвон: AllReduce на коммуникаторе из 8 рангов затрагивает только эти 8, а не всю сеть.
NCCL (сл. 18–23)NVIDIA Collective Communication Library — библиотека, реализующая коллективные коммуникации между GPU с учётом топологии кластера и скорости внутри-/межнодовой связи; выбирает протокол и алгоритм передачи данных.«Логистическая служба» для данных между видеокартами: сама решает, каким маршрутом и какими партиями везти данные, лишь бы быстрее и без дедлоков.
Deadlock (сл. 11)Ситуация взаимного ожидания в point-to-point коммуникации (например, GPU-0 и GPU-1 одновременно ждут данные друг от друга); падает «тихо» — без ошибки, если не настроен таймаут.Два человека одновременно уступают друг другу дорогу в узком проходе и оба стоят на месте — только тут никто не заметит, что что-то пошло не так, пока не кончится терпение (или таймаут).
AllReduce (сл. 12)Коллективная операция: все ранги получают результат редукции (например, суммы) данных со всех рангов. Эквивалентна последовательному Reduce+Broadcast или ReduceScatter+AllGather, но выполняется как одна операция дешевле.Все скидываются в общий котёл и каждый уносит домой одинаковую порцию общего супа.
Broadcast (сл. 13)Тензор с одного (корневого) ранга копируется на все остальные ранги: $\text{out}[i]=\text{in}[i]$.Один человек зачитывает объявление вслух — все остальные записывают себе одно и то же.
AllGather (сл. 14)Каждый ранг хранит часть тензора; в результате каждый ранг получает полный тензор, собранный из частей со всех рангов.Каждый приносит свой кусок пазла, а на выходе у каждого — фото полностью собранной картинки.
ReduceScatter (сл. 16)Совмещение редукции и разбиения: сначала данные редуцируются (например, суммируются) по всем рангам, затем результат делится на части, и каждый ранг получает только свою часть.Общий суп сварили, но вместо того чтобы разлить всем поровну, каждому наливают только его персональную порцию — и не более.
AllToAll (сл. 17)Каждый ранг отправляет разные части своего тензора всем остальным рангам; самая дорогая из коллективных операций (полный обмен «каждый с каждым»).Все участники одновременно обмениваются письмами друг с другом персонально — писем много, и это самый «шумный» вид переписки.
NVLink / NVSwitch (сл. 5–6)NVLink — быстрая прямая связь между парой GPU внутри ноды (в противовес более медленной, но универсальной PCIe-шине); NVSwitch — коммутатор, который избавляет от необходимости тянуть NVLink «все со всеми» напрямую.PCIe — общий коридор общежития; NVLink — личная дверь между соседними комнатами; NVSwitch — вахтёр-диспетчер, через которого можно быстро попасть в любую комнату, не протягивая дверь в каждую лично.
RDMA [вне слайдов]Remote Direct Memory Access — передача данных напрямую от GPU к сетевой карте (NIC), в обход промежуточного копирования через память CPU; используется для межнодовой связи (communications.pdf, §1.3).Курьер забирает посылку прямо со склада, не заезжая в офис за дополнительной бумажной волокитой.
ZeRO (сл. 26–28)Zero Redundancy Optimizer — семейство стадий шардирования данных обучения между рангами вместо их репликации: ZeRO-1 шардирует состояние оптимизатора, ZeRO-2 — дополнительно градиенты, ZeRO-3 (=FSDP) — ещё и параметры.Вместо того чтобы каждый член семьи хранил свою копию всей энциклопедии, том за томом раздаются по одному экземпляру на всех, и все делятся при необходимости.
FSDP (сл. 28)Fully Sharded Data Parallel — практическая реализация ZeRO-3: параметры каждого слоя собираются через AllGather непосредственно перед его вычислением и освобождаются сразу после.Строительная бригада не хранит все инструменты у каждого рабочего — нужный инструмент подвозят на этаж прямо перед тем, как он понадобится.
DDP (сл. 25)Распределённый параллелизм данных: батч делится между рангами, параметры реплицируются, градиенты усредняются через AllReduce.Несколько человек решают одну и ту же контрольную по разным вариантам, а потом сверяют и усредняют итоговые баллы, чтобы у всех была одна и та же «оценка» (веса модели).
Bucketing (запись, сл. 25)Оптимизация DDP: AllReduce по градиентам запускается не после полного backward, а по мере готовности «бакетов» (частей градиента), параллельно с вычислением следующих слоёв backward.Не ждать, пока упакуют все коробки для переезда — грузовик подаётся под первую же готовую партию, а остальные коробки пакуются, пока он едет.
Тензорный параллелизм, TP (сл. 30–34)Разделение вычислений внутри одного слоя (по столбцам и/или строкам матрицы весов) между несколькими рангами; держится строго внутри одной ноды (TP≤8) из-за тяжёлых AllReduce/AllGather.Один и тот же большой чертёж делят на полосы между несколькими чертёжниками, которые работают одновременно, а потом полосы склеивают.
Sequence Parallelism, SP (сл. 35)Разделение самой последовательности (а не матрицы весов) между рангами для Dropout/LayerNorm — операций, которые не параллелятся так же, как TP; используется в паре с TP, $\text{rank(SP)}=\text{rank(TP)}$.Заполняет «щели» в конвейере TP — там, где чертёж делить по столбцам неудобно, его делят по кусочкам самого текста (последовательности).
Ring Attention / контекстный параллелизм, CP (сл. 37–38)Разделение входного контекста между рангами для механизма внимания над очень длинными последовательностями; K/V-блоки передаются по кольцу между GPU, каждый ранг постепенно накапливает статистики внимания по всем блокам.Каждый читает свой кусок книги, но чтобы ответить на вопрос по всей книге, кусочки пересказа передают по кругу, пока каждый не услышит все части.
Zig-Zag Ring Attention (сл. 39)Модификация Ring Attention для причинной (causal) маски: последовательность нарезается не подряд, а «зигзагом» (переднее и заднее полукольцо на один ранг), чтобы выровнять неравномерную из-за маски нагрузку между рангами.Вместо того чтобы одному собирать пазл из тысячи кусочков, а другому — из десяти, кусочки перемешивают так, чтобы у каждого было поровну работы.
AFAB (сл. 41)All-Forward-All-Backward — самое простое расписание конвейерного параллелизма: сначала forward для всех стадий, затем backward для всех стадий в обратном порядке; создаёт большой простой рангов.Сначала вся бригада конвейера собирает изделия от начала до конца, а уже потом та же бригада, в обратном порядке, всё разбирает и проверяет — пока разбирают одно звено, остальные простаивают.
1F1B (сл. 42)One-Forward-One-Backward — расписание PP, при котором backward для готовых микробатчей начинается, не дожидаясь окончания forward по всем стадиям; заметно снижает простой рангов ценой более сложного расписания.Конвейер начинает разбирать и проверять уже готовые изделия, не дожидаясь, пока соберут вообще всё — простоя меньше, но следить за тем, что где происходит, сложнее.
AsyncTP [вне слайдов] (запись, 01:51:00)Асинхронный тензорный параллелизм: построен на «сопряжённых» коллективных коммуникациях, чередующих тензорный и sequence-параллелизм так, чтобы часть синхронизаций между их шагами не требовалась.Вместо того чтобы после каждого шага останавливаться и ждать полной сверки со всеми, часть проверок откладывают и совмещают с уже идущей работой.

Раздел 3. Вопросы для подготовки к защите лабораторных (теория)

Формат ответа: сначала тезис (1–2 предложения), затем аргументация от лица студента, со ссылками на слайды и таймкоды записи. Вопросы 1–3 и 5 воспроизводят реальные вопросы, прозвучавшие на занятии.

1. Почему AllReduce равносилен последовательному выполнению Reduce и Broadcast, и зачем тогда вообще нужна отдельная операция AllReduce?

Тезис: математически AllReduce = Reduce → Broadcast (и отдельно = ReduceScatter → AllGather), но как единая операция AllReduce выполняется быстрее, чем эти пары последовательно.

Аргументация: если сначала выполнить Reduce (результат редукции — только на одном ранге), а потом Broadcast (раздать этот результат всем), получим ровно то же самое, что и AllReduce. Но у последовательного выполнения двух коллективных операций накладные расходы двойные: два запуска ядер, две инициализации ресурсов, лишнее копирование данных между памятью и буфером на каждом шаге. AllReduce как единая операция эти расходы не дублирует (сл. 12–13; запись, 20:03–27:19).

2. В чём разница между способами получить AllReduce «через Reduce+Broadcast» и «через ReduceScatter+AllGather», и почему второй способ обычно предпочтительнее на практике?

Тезис: оба способа дают математически идентичный результат, но ReduceScatter+AllGather делит работу по редукции между рангами, а не концентрирует её на одном корневом ранге.

Аргументация: в паре Reduce+Broadcast вся редукция выполняется на одном ранге, который потом рассылает результат всем — этот ранг временно становится узким местом. В паре ReduceScatter+AllGather каждый ранг сразу считает и хранит лишь свою часть результата (после ReduceScatter), а полный тензор собирается заново уже из готовых частей через AllGather — нагрузка размазана по всем рангам равномерно (сл. 16–17; запись, 28:21–29:57).

3. Где именно нужно разместить функцию активации при тензорном параллелизме FFN-блока (столбец → строка), и почему это не требует дополнительной коммуникации?

Тезис: функцию активации нужно применить к промежуточному выходу первого (столбцового) слоя, прямо на шардированном куске активаций каждого устройства, без предварительного сбора данных.

Аргументация: если бы для применения нелинейности требовалось сначала собрать полный тензор со всех устройств, пришлось бы вставлять лишний AllGather/AllReduce между двумя слоями FFN-блока. Но функция активации применяется поэлементно — результат на шардированном куске совпадает с результатом на полном тензоре, вычисленном для тех же позиций. Поэтому активацию можно применить локально на каждом устройстве сразу после первого (столбцового) умножения, не собирая данные, и единственная коммуникация всего блока остаётся одна — AllReduce в самом конце (сл. 32; запись, 01:07:59–01:11:45).

4. Почему ядро FlashAttention не «ломается», когда тензорный параллелизм считает механизм внимания только для части голов на каждом устройстве?

Тезис: FlashAttention как ядро работает над произвольным числом голов, переданных ему на вход, поэтому раздел голов между устройствами — это просто уменьшение числа голов на входе ядра, а не изменение его логики.

Аргументация: FlashAttention принимает тензор размерности (батч, число голов, длина последовательности, размер головы). При тензорном параллелизме с TP=2 GPU одна GPU просто получает на вход 16 из 32 голов вместо всех 32, вторая — оставшиеся 16; ядро вызывается на каждом устройстве отдельно и обрабатывает ровно то число голов, которое ему передали. Итоговый результат по всем головам получается тем же самым, потому что головы внимания вычисляются независимо друг от друга и математически эквивалентны, посчитаны ли они все сразу или по частям на разных устройствах (сл. 33–34; запись, 01:12:55–01:17:48).

5. В чём разница между Ring Attention и Zig-Zag Ring Attention, и с какой известной вам проблемой лабораторной работы это связано?

Тезис: обычное Ring Attention с наивной (подряд идущей) нарезкой последовательности даёт несбалансированную нагрузку под причинной маской — эта же несбалансированность из-за маски знакома по маскированному вниманию в ЛР2; Zig-Zag перераспределяет блоки последовательности так, чтобы нагрузка выровнялась.

Аргументация: под причинной (causal) маской ранг, отвечающий за самые ранние токены последовательности, реально вычисляет только маленький треугольник маски, а ранг с самыми поздними токенами — почти всю строку целиком; при наивной нарезке на 4 ранга нагрузка получается в соотношении 1:2:3:4. Zig-Zag Ring Attention решает это, отдавая каждому рангу не один смежный кусок последовательности, а два несмежных (например, самый ранний и самый поздний), так что тяжёлые и лёгкие треугольники маски компенсируют друг друга — численно после такой перестановки нагрузка на всех рангах становится одинаковой (проверено в песочнице, Раздел 4.5). Важная оговорка лектора: если маска ещё сложнее, чем простая треугольная (например, «бочная» маска ЛР2 — с дополнительно вырезанными областями), ровно сбалансировать зигзагом уже тяжелее — это не универсальное решение (сл. 37–39; запись, 01:26:11–01:30:40).

6. Почему тензорный параллелизм принято держать строго внутри одной ноды (TP ≤ 8), а не растягивать на несколько нод?

Тезис: коллективные коммуникации TP (AllReduce/AllGather на каждом слое) слишком тяжёлые и не прячутся под вычисления, поэтому их нужно выполнять на самой быстрой доступной связи — то есть внутри ноды.

Аргументация: в отличие от, например, AllReduce градиентов в DDP, который можно спрятать под вычисление следующего слоя backward (bucketing), коммуникации TP (AllReduce после каждого линейного/attention-блока) должны завершиться прежде, чем можно будет двигаться дальше по forward/backward — то есть они на критическом пути и не скрываются под вычислениями. Межнодовая связь заметно медленнее внутринодовой (NVLink/NVSwitch), поэтому вынесение TP за пределы ноды резко увеличило бы время каждого шага. Формально так сделать можно, но на практике не делают — отсюда правило TP≤8, число GPU в стандартной ноде (сл. 35; запись, 01:20:10–01:21:15, 01:42:13–01:42:27).

7. Почему обратная связь при deadlock в point-to-point коммуникациях особенно опасна на практике?

Тезис: deadlock не выдаёт явной ошибки — программа просто зависает («падает тихо»), и без специально настроенного таймаута это трудно отличить от, например, обычной медленной операции.

Аргументация: если ранг A ждёт данные от ранга B, а ранг B в тот же момент ждёт данные от A, оба процесса будут ждать бесконечно — ни один из них не сообщит об ошибке, потому что с точки зрения каждого он всё ещё корректно исполняет операцию receive. Обнаружить проблему можно только по внешним признакам (обучение не продвигается) либо по заранее настроенному таймауту. Именно поэтому реальные системы распределённого обучения избегают выстраивания сложной логики поверх «сырых» point-to-point операций и переходят на более высокий уровень абстракции — коллективные коммуникации с заранее фиксированным, проверенным порядком обмена (сл. 11; запись, 17:35–19:00).

8. Чем принципиально отличаются друг от друга ZeRO-1, ZeRO-2 и ZeRO-3 (FSDP) с точки зрения того, что именно шардируется?

Тезис: три стадии ZeRO шардируют всё больше компонентов состояния обучения — от только состояния оптимизатора (ZeRO-1) до состояния оптимизатора и градиентов (ZeRO-2) и, наконец, ещё и самих параметров модели (ZeRO-3/FSDP).

Аргументация: ZeRO-1 шардирует только состояние оптимизатора (самое «тяжёлое» по памяти при Adam/AdamW — 8 из 16 байт на параметр в примере со слайда), после обычного AllReduce градиентов каждый ранг обновляет лишь свою часть, а актуальные параметры затем собираются заново. ZeRO-2 дополнительно шардирует градиенты: вместо AllReduce используется ReduceScatter, и каждый ранг сразу получает и хранит только свою часть градиента. ZeRO-3 (=FSDP) шардирует уже и сами параметры: перед вычислением каждого слоя нужно собрать его параметры через AllGather, а после backward — снова разложить градиенты через ReduceScatter. Чем глубже стадия шардирования, тем меньше памяти на одном ранге (в примере со слайда — с 120 ГБ до 1.9 ГБ), но тем больше становится давление на сеть коммуникациями (сл. 26–28; запись, 51:55–56:24).

9. Почему алгоритм Tree выгоднее алгоритма Ring при большом числе рангов в NCCL?

Тезис: сложность коммуникации Ring растёт линейно с числом рангов $O(N)$, а Tree — логарифмически $O(\log N)$, поэтому при тысячах рангов Tree требует на порядки меньше шагов.

Аргументация: в кольцевом алгоритме данные обходят всех N рангов по очереди — число шагов пропорционально N (при 1000 рангах — порядка 1000 пересылок). В древовидном алгоритме данные поднимаются от листьев к корню и распространяются обратно вниз — глубина дерева растёт как $\log N$ (для 1000 рангов — порядка 10 шагов). Обратная сторона Tree — GPU у корня дерева получают больше данных, чем листовые GPU, создавая «бутылочные горлышки»; поэтому на практике внутри ноды (где рангов немного, а связь быстрая) выгоднее Ring, а между нодами (где рангов может быть много, а связь медленнее) — Tree, что и реализует иерархический алгоритм NCCL (сл. 21–23; запись, 37:29–42:03).

10. В чём суть асинхронного тензорного параллелизма (AsyncTP), упомянутого лектором в конце занятия?

Тезис: AsyncTP снижает число обязательных синхронизаций между шагами тензорного и sequence-параллелизма за счёт «сопряжённых» (перекрывающихся) коллективных коммуникаций, но не убирает синхронизации полностью.

Аргументация: при обычном чередовании TP и SP каждый переход между ними требует полной синхронизации (AllReduce/AllGather должны завершиться, прежде чем можно двигаться дальше). AsyncTP выстраивает эти коммуникации так, чтобы часть шагов могла перекрываться с уже идущими вычислениями или с другими коммуникациями, не дожидаясь полного завершения предыдущего шага. Полностью избавиться от синхронизаций не получается — например, перед механизмом внимания всё равно нужно собрать всю последовательность целиком, — но их общее число заметно сокращается (запись, 01:51:00–01:51:59; на слайдах не показано).

4.5. Скелет решения ЛР (исполнен в песочнице без ошибок)

"""
Раздел 4.5. Проверка баланса нагрузки: наивное кольцевое внимание (Ring Attention)
против Zig-Zag Ring Attention под причинной (causal) маской.

Связь с ЛР2: маскированное многоголовое внимание (block-masked attention) из ЛР1/ЛР2
использует ту же причинную маску, что и здесь; лектор прямо просил (запись, 01:27:46)
спрогнозировать проблему при расширении такого внимания до контекстного параллелизма.

Считаем, сколько (query, key) ячеек причинной маски реально приходится вычислять
каждому из N_RANKS рангов при двух схемах нарезки последовательности на chunks,
и сравниваем максимальный разброс нагрузки между рангами.
"""
import numpy as np

N_TOKENS = 16   # как на слайдах 37-39 (причинная маска 16x16)
N_RANKS = 4     # как на слайдах 37-39 (4 GPU)
chunk = N_TOKENS // N_RANKS            # 4 токена/ранг при наивной нарезке
sub = N_TOKENS // (2 * N_RANKS)        # 2 токена/под-чанк при zig-zag (2 под-чанка/ранг)

# причинная маска: строка i (query) видит столбец j (key) <=> j <= i
i_idx, j_idx = np.meshgrid(np.arange(N_TOKENS), np.arange(N_TOKENS), indexing="ij")
causal = (j_idx <= i_idx)

# --- наивная нарезка (сл. 37-38): ранг r владеет query-строками [r*chunk : (r+1)*chunk) ---
naive_load = [int(causal[r * chunk:(r + 1) * chunk, :].sum()) for r in range(N_RANKS)]

# --- zig-zag (сл. 39): ранг r владеет под-чанком r "спереди" и под-чанком (2N-1-r) "сзади" ---
zz_load = []
for r in range(N_RANKS):
    front = causal[r * sub:(r + 1) * sub, :]
    back_idx = 2 * N_RANKS - 1 - r
    back = causal[back_idx * sub:(back_idx + 1) * sub, :]
    zz_load.append(int(front.sum() + back.sum()))

assert sum(naive_load) == sum(zz_load) == int(causal.sum()), "тотал должен совпадать -- иначе схемы не эквивалентны по объёму работы"

def imbalance(loads):
    return round(max(loads) / min(loads), 2)

print(f"Токенов: {N_TOKENS}, рангов: {N_RANKS}, токенов/ранг: {chunk}")
print(f"Наивная нарезка (сл. 37-38):  нагрузка по рангам = {naive_load}"
      f"  (max/min = {imbalance(naive_load)})")
print(f"Zig-Zag нарезка (сл. 39):     нагрузка по рангам = {zz_load}"
      f"  (max/min = {imbalance(zz_load)})")
print(f"Суммарно причинных ячеек = {int(causal.sum())} (= N(N+1)/2 = {N_TOKENS*(N_TOKENS+1)//2})")

Результат прогона: при 16 токенах и 4 рангах (числа со сл. 37–39) наивная нарезка причинной маски даёт нагрузку по рангам [10, 26, 42, 58] — то есть отношение максимума к минимуму 5.8×, ровно подтверждая слова лектора «для первой гопушки мы вычисляем только один блок... а для четвёртой — все» (запись, 01:25:03–01:26:11). Zig-Zag-нарезка выравнивает нагрузку до [34, 34, 34, 34] (отношение 1.0×) при том же суммарном объёме вычислений (136 причинных ячеек = $N(N+1)/2$ для $N=16$) — количественное подтверждение того, зачем нужен Zig-Zag Ring Attention.
