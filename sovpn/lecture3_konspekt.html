§1. Анатомия GPU (сл. 3–16)

1.1. Почему мы используем GPU? (сл. 3–6)

Один линейный слой записывается как $y = xW + b$ (сл. 3). При перемножении и сложении матриц и векторов каждый элемент результата вычисляется независимо от остальных. На CPU этот факт почти бесполезен — вычисления всё равно идут последовательно; на GPU он позволяет считать элементы параллельно (сл. 3).

CPU минимизирует задержку (latency) — то есть время выполнения последовательности операций; GPU максимизирует пропускную способность (throughput) — количество операций в единицу времени. Но не все модули нейронной сети одинаково легко распараллеливаются (сл. 4–5).

Рисунок (сл. 6). «Почему мы используем GPU?». Схема сравнения архитектур: слева CPU — несколько крупных ядер (Core), у каждого свой блок Control и L1 Cache, пары ядер делят L2 Cache, все ядра — общий L3 Cache поверх DRAM; справа GPU — плотная решётка мелких вычислительных элементов (зелёные квадраты) с одним общим L2 Cache поверх DRAM, без промежуточных уровней L1/L3 и почти без блоков Control.
Из записи лекции [03:39–06:01]

Лектор поясняет схему: у CPU по сравнению с GPU значительно меньше вычислительных ядер, но гораздо больше кэша — для хранения промежуточных и часто повторяющихся результатов — и гораздо больше «управляющих» блоков на ядро (в том числе логика предсказания ветвлений). У GPU управляющих блоков на ядро гораздо меньше: один блок Control там отвечает сразу за несколько вычислительных элементов, зато самих вычислительных элементов значительно больше.

На пальцах

CPU — как один многоопытный повар: готовит одно сложное блюдо быстро и качественно, но по одному шагу за раз. GPU — как цех из тысяч поварят на конвейере: каждый умеет только нарезать один и тот же овощ, зато режут все одновременно. Если блюдо — это, например, сложение двух векторов длины 4096, GPU нарежет (сложит) все 4096 пар чисел за один «такт конвейера», а CPU — по одной паре за раз, пусть и очень быстро.

1.2. Streaming Multiprocessors (сл. 7)

GPU состоит из большого числа вычислительных блоков — Streaming Multiprocessors (SM). В некотором смысле SM — это как ядро в CPU (сл. 7).

Рисунок (сл. 7). Архитектура NVIDIA GPU. Слева блок CPU: несколько CPU Core с общим Memory Controller, L3 Cache и портом PCIe/NVLink, подключённый к System DRAM. Справа блок GPU: Memory Controller и общий L2 Cache, к которому подключены несколько групп GPC (Graphics Processing Cluster), в каждой — несколько SM с собственным Unified Data Cache/L1 Cache/Shared Memory и Register File; GPU подключён к своей GPU DRAM и к CPU через порт PCIe/NVLink.
Из записи лекции [06:01–06:57]

Связь CPU и GPU происходит через NVLink или порт PCI Express; подробнее об этом лектор обещал рассказать на пятой лекции курса (про распределённое обучение).

1.3. Потоки, варпы и SIMT (сл. 8–10)

Когда вычисления на GPU запускаются, задача разбивается на большое число потоков (threads): например, при сложении двух векторов $c_i = a_i + b_i$ один поток отвечает за вычисление одного элемента. Потоки группируются в варпы — потоки и варпы являются программными, а не аппаратными единицами: они не имеют «физического» представления на кристалле GPU (сл. 8).

Варп — группа из 32 потоков, исполняемых вместе; варп является базовой единицей исполнения инструкций на GPU: одна инструкция применяется сразу ко всем потокам варпа. Все потоки внутри варпа в каждый момент времени либо исполняют одну и ту же инструкцию, либо не работают. Такой принцип называется SIMT — Single Instruction, Multiple Threads (сл. 9–10).

Из записи лекции [07:25–08:42]

Лектор уточняет и сам себя поправляет: «потоки выполняются у нас параллельно, но не совсем независимо» — именно потому, что они собраны в варпы и вынуждены в каждый момент разделять одну общую инструкцию.

На пальцах

SIMT — как дирижёр, подающий одну и ту же команду («играть форте») сразу 32 музыкантам: каждый играет свою партию (свои данные), но по единой на всех команде и в едином такте. Если кто-то из музыкантов должен внезапно замолчать — оркестр всё равно играет тем же тактом, просто у одного пульт громкости на нуле.

1.4. Расхождение варпа (warp divergence) (сл. 11)

Если в программе есть логическое ветвление, может появиться несколько версий инструкции; все эти версии будут выполняться по очереди. Это называется расхождением варпа (сл. 11).

Рисунок (сл. 11). «Расхождение варпа». Слева — псевдокод: if (groupThreadID.x < 4) { A; B; } else { X; Y; } Z;. Справа — временная диаграмма: единый поток потоков (стрелки) сначала «расходится» (diverge) на две зелёные полосы — одна выполняет A;B, другая X;Y, — а затем «сходится» (reconverge) обратно в одну полосу для выполнения Z; ось времени подписана Time.
Из записи лекции [08:42–10:57]

Лектор разбирает пример с кода на слайде: потоки с индексом меньше 4 выполняют инструкции A и B, остальные — X и Y. До ветвления все потоки варпа шли параллельно; после — варп сначала выполняет ветку A;B (потоки другой ветки маскируются, то есть отключаются и простаивают), затем — ветку X;Y (маскируются уже первые потоки). Проблема здесь двойная: во-первых, суммарно выполняется значительно больше инструкций, во-вторых, это сильно замедляет программу, потому что параллелизм внутри варпа ломается.

На пальцах

Представьте бригаду из 32 маляров, красящих забор по одной и той же команде мастера. Мастер крикнул «красим красным!» — 16 маляров, у кого была красная краска, красят, остальные 16 стоят и ждут. Потом мастер крикнул «красим синим!» — теперь красят те, у кого синяя, а первые 16 простаивают. Хотя маляров 32, забор красится со скоростью работы 16 — ровно то, что происходит с варпом при расхождении.

1.5. CUDA-ядра и тензорные ядра (сл. 12–13)

CUDA-ядра — это ALU (арифметико-логические устройства) внутри SM. Существуют версии под разные типы данных: из типов с плавающей точкой интересны fp32, fp16, fp8, fp4, а также версии под целочисленные значения (сл. 12). Тензорные ядра — специализированные ядра для матричных умножений; на GPU их значительно меньше, чем CUDA-ядер — обычно от 1 до 4 на SM (сл. 13).

Рисунок (сл. 12–13). Структура SM. Прямоугольник SM разбит на 4 одинаковых подблока; в каждом — L0 Instruction Cache, Warp Scheduler (32 thread/clk), Dispatch Unit, Register File (16 384 × 32-bit), сетка ячеек CUDA-ядер разных типов (INT32, FP32, FP64), один блок TENSOR CORE и ряд блоков LD/ST и SFU; внизу всех четырёх подблоков — общие 192KB L1 Data Cache/Shared Memory и блоки Tex.
Из записи лекции [10:57–13:27]

По личным наблюдениям лектора, тип FP64 в нейросетях практически не используется («я, например, ни разу не видел, чтобы кто-то в нейронках использовал тип FP64»); рабочая лошадка — FP32, ниже по точности — FP16/FP8/FP4. CUDA-ядра под целочисленные вычисления появились начиная с архитектуры Turing; FP32-ядра также умеют целочисленную арифметику, поэтому в части сценариев FP32-ядра могут подменять INT32-ядра. Конкретный числовой пример архитектуры: если на одном SM 128 CUDA-ядер FP32, тензорных ядер там же — всего около 4 (само число варьируется от 1 до 4 в зависимости от архитектуры).

На пальцах

CUDA-ядро — это человек с калькулятором: за раз одно умножение или сложение. Тензорное ядро — небольшая бригада, которая одним слаженным действием перемножает и складывает сразу целый маленький блок чисел (кусочек матрицы) — как автопогрузчик вместо переноски коробок руками: мощнее, но такой инструмент один на 32–128 «людей с калькуляторами», и годится он не для любой задачи, а именно для матричного умножения.

1.6. Варп-планировщики (сл. 14–16)

Внутри SM есть аппаратные блоки, которые выбирают, какой варп будет запущен — варп-планировщики; варпы не запускаются одновременно, поскольку часть из них может быть готова раньше, а другая часть — позже (сл. 14). Варпы делятся на активные и неактивные; активные — те, что заняли ресурсы SM. Максимально на SM может быть запущено одновременно ограниченное число варпов (это число зависит от архитектуры — например, 32, 48 или 64) (сл. 15). Варпы запускаются по очереди варп-планировщиками. CPU в подобной ситуации минимизирует задержку за счёт сложных кэшей, предсказаний ветвлений и других инженерных хитростей; задача варп-планировщика на GPU — запускать варпы так, чтобы задержка выполнения всей программы уменьшалась за счёт того, что выполнение одного варпа перекрывается работой другого варпа (сл. 16).

Из записи лекции [13:27–17:19]

Число варп-планировщиков на SM обычно равно 4. Числовой пример ограничения по ресурсам: если программе на 16 активных варпах не хватает регистровой памяти и при компиляции задан явный лимит не пересекать границы регистровой памяти, на SM запустится только 16 варпов — даже если архитектура допускает максимум 64. GPU не столько уменьшает задержку, сколько перекрывает её полезной работой других варпов, пока один варп ждёт данные.

На пальцах

Варп-планировщик — как хостес в ресторане на 4 подхода к столикам сразу: рассаживает готовые группы (варпы) за свободные столики (ресурсы SM) по мере готовности; если у столика ещё не убрали посуду с прошлой группы (варп ждёт данные из памяти), хостес не заставляет гостей стоять без дела — она тут же сажает другую готовую группу за соседний стол.

§2. Иерархия памяти (сл. 18–32)

2.1. Иерархия памяти (сл. 18)

Данные нужно где-то хранить. Обращение к памяти — не мгновенно; невозможно сделать память одновременно и самой быстрой, и максимально объёмной. Появляется иерархия: чем память ближе к вычислениям, тем она быстрее, но меньше (сл. 18).

Именно эта иерархия — прямая подготовка к следующей лекции курса про Flash Attention.

2.2. H2D обмен данными (сл. 19–20)

Наиболее объёмная и самая медленная память — память диска; после диска данные попадают в оперативную память хоста, где делятся на страницы (сл. 19). Копирование данных с хоста на девайс не бесплатное: память хоста удобно делить на страницы для CPU, а для GPU удобнее работать с закреплённой (pinned) памятью (сл. 20).

Рисунок (сл. 19–20). «Pageable Data Transfer» vs «Pinned Data Transfer». Две схемы копирования Host→Device: в первой (Pageable) данные хоста сначала лежат в Pageable Memory и копируются в промежуточный буфер Pinned Memory, только затем — в DRAM устройства; во второй (Pinned) данные хоста сразу лежат в Pinned Memory и копируются в DRAM устройства напрямую, без промежуточного шага.
Из записи лекции [18:29–20:58]

Страницы — это непрерывные адреса виртуальной памяти: физически ячейки могут быть разбросаны, но ОС выстраивает их подряд для удобства работы с CPU. Для передачи данных на девайс нужно, чтобы адрес данных был физически зафиксирован — поэтому адрес «закрепляют» перед копированием. Указание к ЛР (20:58). Чтобы не тратить время на закрепление адресов во время самого обучения, данные можно закрепить в памяти заранее: например, после токенизации текста и получения индексов batch — именно для этого в DataLoader выставляют pin_memory=True.

На пальцах

Pageable-память — как книги в общей библиотеке, которые библиотекарь (ОС) в любой момент может переставить на другую полку. Прежде чем курьер (DMA-контроллер) заберёт книгу для доставки, библиотекарь должен временно «заморозить» её на одном месте (это и есть закрепление/pinning) — лишний шаг. Pinned-память — как книги на персональной полке курьера: их никто не переставляет, и курьер может забирать их сразу, без лишнего шага «заморозки».

2.3. Глобальная память (GMEM) (сл. 21–23)

Глобальная память — основная, самая объёмная и самая медленная память GPU (хотя обращение к ней значительно дороже обращения к памяти хоста). Часто задача оптимизации программы на GPU будет заключаться в оптимизации доступа к глобальной памяти. Через GMEM также происходит общение между разными программами на одном девайсе и между несколькими девайсами (сл. 21–23).

Из записи лекции [20:58–23:37]

Основная суть большинства оптимизаций на GPU — обращаться к глобальной памяти реже. В GMEM чаще всего хранятся веса и активации нейронной сети.

Вне слайдов

Если параметры, активации или данные не помещаются в память устройства целиком, их часть выгружают в память хоста — такой приём называется cpu offloading.

2.4. Разделяемая память (SMEM) и конфликт банков (сл. 24–25)

SMEM — следующий уровень иерархии: намного меньше GMEM, но доступ быстрее на несколько порядков; SMEM позволяет обмениваться данными потокам одного варпа (сл. 24). Проблема: SMEM физически разбита на несколько банков; если несколько потоков одновременно обращаются к адресам одного банка, доступ выполняется медленнее — это называется конфликтом банков (сл. 25).

Рисунок (сл. 25). «Конфликт банков». Две группы по 16 ячеек памяти (Thread 0…Thread 15 → Bank 0…Bank 15) с линиями обращений: слева линии идут по порядку без пересечений (нет конфликта), справа линии многократно пересекаются — несколько потоков указывают на одни и те же банки (конфликт).
Из записи лекции [23:37–24:46]

Доступ быстрее в 10–100 раз, чем к глобальной памяти. SMEM обслуживает данные не только внутри варпа: забегая вперёд, лектор уточняет, что реально речь идёт о данных внутри нескольких варпов одного блока потоков. Конфликт банков обычно решается добавлением небольшого паддинга к блокам разделяемой памяти.

2.5. Регистровая память (RMEM) (сл. 26–27)

Самая быстрая память в иерархии — регистровая; доступ к ней выполняется практически мгновенно, за 1–2 такта. Операции выполняются над данными, находящимися в регистрах; данные в регистрах доступны только своему потоку (сл. 26). Регистровая память представлена как Register File, разбитый на ячейки по 32 бита — регистровые ячейки. Ресурсы регистров ограничены: если регистров не хватает, компилятор использует медленную local memory (сл. 27).

Из записи лекции [24:46–29:06]

В одну регистровую ячейку (32 бита = 4 байта) можно записать один элемент FP32, либо, в векторизованном виде, несколько элементов меньшей разрядности — например, два числа FP16 (по 16 бит) или четыре числа FP8: программе ячейка видна как один «векторный» элемент, но внутри явно разделена на части. Без такой векторизации даже 4-битный элемент займёт всю ячейку целиком. Регистровая память обычно чуть меньше по объёму, чем разделяемая память SM. Если регистров не хватает, по умолчанию компилятор использует более медленную local memory (скорость обращения к ней сравнима со скоростью обращения к глобальной памяти) — Уточнение: отдельно лектор упоминает и другой возможный исход при явном лимите на компиляции — программа завершается с ошибкой, а не тихо использует local memory; оба поведения совместимы: без ограничения — тихий спиллинг в local memory (термин из письменного текста лектора — register spilling), с явным лимитом — явная ошибка компиляции/выполнения. Лектор рекомендует именно второй вариант — явно ограничивать использование регистров, — чтобы не ловить тихие, трудноуловимые просадки производительности.

На пальцах

Регистр — это карман на рубашке потока: положить туда можно быстро, достать — мгновенно, но карман один на человека, и он крохотный (32 бита). Если данных больше, чем карманов, — либо приходится носить лишнее в рюкзаке (local memory, почти как GMEM по скорости), либо (если старшийсмены прямо запретили брать рюкзак) поход вообще не начнётся — программа не скомпилируется/упадёт.

2.6. L1 и L2 кэш (сл. 28)

L1-кэш находится внутри SM и кэширует часть обращений к глобальной памяти; на современных видеокартах NVIDIA L1-кэш и разделяемая память часто используют общий физический ресурс — соотношение их размеров не фиксировано: чем больше используется SMEM, тем меньше остаётся места под L1. L2-кэш общий для GPU: через него проходят все обращения разных SM к глобальной памяти (сл. 28).

Из записи лекции [29:06–31:32]

Уточнение: всё сказанное про устройство памяти относится только к видеокартам Nvidia — у AMD архитектура иная, и такие карты редко используют для обучения нейронных сетей, поэтому курс их не рассматривает. Соотношение L1/SMEM обычно настраивается драйвером автоматически, в зависимости от того, сколько разделяемой памяти запрашивает программа.

2.7. Согласованный доступ к памяти (сл. 29–32)

Потоки исполняются варпами; если потоки одного варпа обращаются к соседним ячейкам памяти, GPU может объединить эти обращения в одну транзакцию, что кратно снижает стоимость обращения к памяти (сл. 29).

Размер одной транзакции определяется характеристиками конкретной архитектуры и может составлять от 128 до 8192 бит — например, у карты A100. Разбирая рисунки «Хорошо»/«Плохо», лектор задал устный числовой пример: шина памяти 256 бит, одна ячейка данных — 32 бита. Расхождение (34:24–35:59). На вопрос «сколько будет транзакций в согласованном случае» студент (Богдан) отвечает «две», лектор соглашается («да, да»); для рассинхронизированного случая — верно указано «столько же, сколько ячеек» (32). Число 32 для несогласованного случая верно (каждая из 32 ячеек — отдельная транзакция, ничего объединить нельзя). Чему верить на защите: пользуйтесь формулой $\lceil (N \cdot \text{размер ячейки}) / \text{размер шины} \rceil$; неверная «двойка» могла быть и огрехом распознавания речи, а не ошибкой по существу, поэтому не стоит бездумно её запоминать.

Дальше на примере наивного матричного умножения лектор поясняет рисунок 32: если матрица данных X хранится по строкам (Row-Wise) — чтение вдоль строки идёт по соседним адресам, доступ согласован. У матрицы весов W (в примере — B на рисунке) при обращении по столбцам последовательные элементы столбца лежат в памяти далеко друг от друга — доступ не согласован. Указание к ЛР (40:37–42:14). Решение — хранить матрицу-оператор (в нейросетях это чаще всего матрица весов) в транспонированном виде: тогда обращение к столбцу исходной матрицы становится обращением к строке транспонированной, и оно снова последовательно. По словам лектора, в обычной CUDA данные по умолчанию записываются в Row-Wise формате (в cuBLAS/cuBLASLt соглашения о формате отличаются — этот фрагмент по транскрипту не восстанавливается точно, лектор сам путается в формулировке).

Представьте склад с полками, где каждая полка — это 32 байта (наша «транзакция»), а каждая коробка — это 4 байта (наша «ячейка»). §3. Метрики производительности GPU (сл. 34–41)

3.1. Задержка и пропускная способность (сл. 34–35)

Важно оценивать эффективность работы GPU и программы на GPU. Первое, что приходит в голову — замерять end-to-end время работы; эта метрика называется задержкой (latency) работы программы (сл. 34). Но GPU спроектированы для максимизации объёма работы в единицу времени, поэтому нужно также оценивать пропускную способность (throughput) (сл. 35).

Из записи лекции [42:14–43:33]

Практический способ измерить задержку: поставить отметку времени «старт» перед запуском программы и «end» сразу после завершения; задержка = end − старт. Уменьшать задержку программы тоже полезно, но именно на её минимизацию GPU не проектируют — это задача, для которой оптимален CPU.

3.2. FLOP/s (сл. 36)

Одна из основных характеристик вычислительной производительности — количество операций с плавающей точкой в единицу времени, FLOP/s. Производитель указывает пиковое значение — теоретический предел; важно отличать это значение от реально достижимого. FLOP/s сильно зависит от типа данных, в которых происходят вычисления (сл. 36).

Из записи лекции [44:50–49:06]

Пиковое значение FLOP/s в характеристиках — во многом маркетинговая цифра, посчитанная инженерами производителя в лаборатории; достичь её на реальной программе практически невозможно. Хорошо оптимизированное обучение трансформера на практике достигает примерно 40–70% от пикового FLOP/s. Причина зависимости FLOP/s от типа данных — ядро для FP16 логически проще (меньше транзисторов), чем ядро для FP32, поэтому выполняется быстрее. Вопрос лектора для самопроверки (46:05–49:06): при одинаковом числе CUDA-ядер под FP32 и под INT32 на одном SM что будет больше — FLOPS или INT-OPS? Правильный ответ — INT-OPS: операции с целыми числами выполняются быстрее операций с плавающей точкой, поскольку логическая схема целочисленного ALU проще и короче.

3.3. Memory bandwidth (сл. 37)

Для памяти одна из основных метрик — пропускная способность памяти (memory bandwidth). Если программа читает $R$ байт и записывает $W$ байт за время $t$, пропускную способность можно оценить как $(R+W)/t$ (сл. 37).

3.4. Арифметическая интенсивность (сл. 38)

Одни программы могут быть ограничены пропускной способностью памяти в большей степени, другие — в меньшей; для оценки вводится метрика арифметической интенсивности: $\text{ArithmeticIntensity} = \text{FLOP/s} \;/\; \text{MemoryBandwidth}$. Упрощая (сокращая по времени $t$): $\text{ArithmeticIntensity} = \text{FLOPs}/(W+R)$ (сл. 38).

Из записи лекции [50:15–51:25]

Арифметическая интенсивность позволяет решить, в какую сторону выгоднее оптимизировать программу, но сама по себе не даёт оценки максимальной производительности — числовой пример такого расчёта для поэлементного сложения тензоров лектор разбирает позже, уже в §4.1, на примере типовых операций нейросетей.

3.5. Roofline-модель (сл. 39–40)

Для грубой оценки максимальной производительности используется roofline-модель: $\text{Performance} \le \text{ArithmeticIntensity} \cdot \text{MemoryBandwidth}$ и одновременно $\text{Performance} \le \text{PeakFLOP/s}$, то есть $\text{Performance} \le \min(\text{ArithmeticIntensity}\cdot\text{MemoryBandwidth},\, \text{PeakFLOP/s})$ (сл. 39).

§4. Типовые операции нейронных сетей на GPU (сл. 43–49)

4.1. Поэлементные операции (сл. 43)

Самый простой тип — поэлементные операции: например, сложение тензоров $c_i = a_i + b_i$ (в архитектуре трансформера — это, в частности, residual connections), либо поэлементное применение функций активации, например ReLU: $y_i = \max(0, x_i)$. Поэлементные операции обладают очень низкой арифметической интенсивностью (сл. 43).

Из записи лекции [1:05:29–1:07:52]

Лектор возвращается к нейросетям: типовые операции, которые стоит рассмотреть через призму вычислений на GPU. Складывать можно вектора, матрицы, тензоры любой размерности — например, остаточные связи (residual connections). Другой пример поэлементной операции — функция активации ReLU: для каждого элемента проверяется, больше он нуля или нет, и записывается либо он сам, либо 0.

Из записи лекции [1:07:52–1:13:24]

Расхождение (1:07:52–1:13:24), с уточнением лектора после занятия. В записи ReLU разбирается как ручная реализация через условный оператор: «записываем в память x [если x>0]. Else записываем в память ноль» — и на вопрос, вызовет ли такой код расхождение варпа, лектор в моменте отвечает «нет»: обе ветки якобы выполняют одну и ту же инструкцию записи, просто с разными данными, а значит выполняются параллельно. После занятия лектор сам уточнил, что пример был неудачным: код вида

uint32_t i = ...; // id потока
float x = x[i];
if (x > 0) {
    out[i] = x;
} else {
    out[i] = 0;
}

расхождение варпа как раз вызывает — потому что ветки здесь выполняют не одну и ту же инструкцию: одна ветвь пишет в out[i] значение, уже прочитанное из памяти, другая — константу, минуя чтение. А вот тернарный (предикатный) вариант расхождения не вызывает, поскольку компилируется в одну предикатную инструкцию без реального ветвления:

float x = x[i];
out[i] = x > 0.0f ? x : 0.0f;

Ещё лучше для ReLU — воспользоваться готовой аппаратной функцией библиотеки CUDA, она и быстрее:

out[i] = fmaxf(x[i], 0.0f);

Общий вывод из записи остаётся в силе и без привязки к неудачному примеру: не всякое условное ветвление приводит к расхождению варпа (простые логические операции по типу or/and/xor ветвлений не создают и исполняются внутри GPU без проблем), но в целом лучше по возможности избегать if в GPU-коде и использовать вместо них логические операции или готовые функции библиотеки.

Из записи лекции [1:13:24–1:21:38]

Лектор вместе со студентами считает арифметическую интенсивность поэлементного сложения тензоров в FP32: операция читает два числа (элементы тензоров A и B) и записывает одно (результат C) — 2 операции чтения + 1 операция записи = 3 перемещения по 4 байта (FP32 = 32 бита) = 12 байт; при этом выполняется всего 1 операция с плавающей точкой (само сложение). Итог: $\text{AI} = 1/12$ — на roofline-графике это далеко слева, производительность там «на нуле»: поэлементные операции сильно ограничены памятью (memory bound).

На пальцах

AI = 1/12 означает: на каждый один «удар молотком» (одну арифметическую операцию) уходит 12 байт беготни туда-обратно до склада (глобальной памяти). Молотком стучать — доли такта, до склада бежать — сотни тактов: почти всё время программа не считает, а ждёт данные.

4.2. Редукции (сл. 44)

В нейронных сетях часто встречаются редукции — операции, которые преобразуют массив элементов в скаляр; в отличие от поэлементных операций, они параллелизуются сложнее и также обладают низкой арифметической интенсивностью (сл. 44).

Из записи лекции [1:21:38–1:26:32]

Самая частая редукция во всех нейросетях — вычисление функции потерь (loss): чтобы задать отношение порядка «меньше/больше» и запустить обратное распространение, многомерный выход сети нужно свести к одному скаляру — это и есть редукция, часто даже не одна (например, в MSE — среднее по объектам батча и среднее по элементам). Поскольку считать loss на хосте слишком медленно, редукцию приходится выполнять прямо на GPU — а значит, разработчику нужно уметь реализовывать редукции эффективно внутри SM.

4.3. GEMV (сл. 45)

GEMV — умножение вектора на матрицу, например преобразование одного вектора линейным слоем: $y = xW$. Такая операция часто встречается при инференсе трансформера с использованием KV-кэша (сл. 45).

Из записи лекции [1:27:56–1:29:06]

При обучении трансформеров операция GEMV встречается очень редко (лектор: «мне даже сразу в голову не приходит пример») — почти всегда речь идёт об умножении матрицы на матрицу. Зато при инференсе с KV-кэшем GEMV встречается повсеместно; разбор KV-кэша лектор анонсирует на одну из следующих лекций курса.

4.4. GEMM (сл. 46–48)

GEMM — операция матричного умножения, самая важная операция для нейронных сетей, поскольку описывает линейный слой: $Y = XW$. Каждый элемент $Y$ вычисляется независимо от других, а значит — параллельно; в наивном случае один поток вычисляет скалярное произведение строки на столбец: $Y_{ij} = \sum_{k=1}^{D} X_{ik}W_{kj}$. Такой подход имеет крайне низкую арифметическую интенсивность и требует оптимизации (сл. 46–48).

Из записи лекции [1:29:06–1:41:36]

Наивный подход хорошо ложится на параллелизм GPU, но не учитывает архитектуру памяти: строка $X$ длиной $D$ и столбец $W$ той же длины целиком не помещаются в регистры одного потока, а значит для вычисления одного элемента $Y_{ij}$ нужно многократно обращаться к глобальной памяти. На конкретном примере матриц $7\times7$: 14 операций чтения (7 из строки + 7 из столбца) + 1 операция записи; операций с плавающей точкой — 13 (7 умножений + 6 сложений для скалярного произведения длины 7). В общем виде для размерности $D$: чтений $2D$, запись $1$, FLOPs $2D-1$. Расхождение с письменным конспектом (личные записи 2.md, «арифметическая интенсивность наивного GEMM: d/4»). Формула $d/4$ подразумевала бы рост интенсивности вместе с размером матрицы — это неверно: интенсивность считается как FLOPs/байты $=(2D-1)/(4(2D+1))$, и при росте $D$ она не растёт, а сходится к константе $1/4=0{,}25$ (уже при $D=128$ отличие от $0{,}25$ меньше процента, проверено расчётом). Именно такую константу ($\approx 0{,}25$) лектор и называет в записи как итоговое значение — «ужасно» низкое, сравнимое с поэлементными операциями. Указание к ЛР (1:40:25–1:41:36). Оптимизации наивного GEMM (разбиение на блоки с кэшированием в SMEM) лектор явно анонсирует на «следующую пару» — семинар/следующее занятие; после такой оптимизации арифметическая интенсивность может вырасти примерно до 240, что для roofline-модели этого класса видеокарт (A100) соответствует уже compute-bound режиму — в этом главное преимущество вычисления матричных умножений нейросетей на GPU.

На пальцах

Проверка предела на калькуляторе: при $D=1024$ формула $(2D-1)/(4(2D+1))$ даёт $0{,}2498$, при $D=4096$ — $0{,}2499$: с ростом матрицы число только приближается к $1/4$ снизу, а не растёт вместе с $D$, как можно было бы подумать по записи «d/4».

4.5. Нормализация (сл. 49)

Нормализации используются почти во всех современных архитектурах; на примере LayerNorm: $y_j = \gamma_j \dfrac{x_j-\mu}{\sqrt{\sigma^2+\varepsilon}} + \beta_j$, где $\mu = \tfrac1D\sum_{j=1}^D x_j$, $\sigma^2=\tfrac1D\sum_{j=1}^D (x_j-\mu)^2$. LayerNorm выполняется по одному токену независимо; для каждого токена нужно выполнить редукции — посчитать среднее и сумму квадратов для дисперсии. Нормализация — memory-bound операция с большим количеством синхронизаций (сл. 49).

Из записи лекции [1:43:08–1:51:53]

В трансформерах на каждый подблок может приходиться по 2 слоя нормализации. В наивной реализации (например, при последовательном исполнении операций PyTorch без слияния) вычисление разбивается на пять отдельных программ (кернелов) подряд: (1) редукция для среднего, (2) редукция для дисперсии, (3) поэлементное вычитание/деление, (4) поэлементное умножение на $\gamma$, (5) поэлементное сложение с $\beta$ — и первые две уже сами по себе низкоинтенсивные редукции. Каждая из пяти программ в начале читает данные из глобальной памяти, делает немного вычислений и сразу же кладёт результат обратно в глобальную память — а следующая программа тут же читает его снова оттуда же. Нормализация одного токена вычисляется одним блоком потоков (не одним потоком и не одним варпом), и обычно на один SM выделяется от 1–2 до 32 таких блоков, так что весь нормализующий слой считается почти на всех SM видеокарты сразу. Указание к ЛР (1:49:12–1:50:25). Лектор прямо ссылается на ЛР2: «если вы делали вторую лабораторную работу и вдруг захотите провести профилирование модели… сравните с лайер-нормами — вы ужаснётесь, потому что увидите, что лайер-нормы занимают больше половины времени вычисления», хотя по объёму арифметики там «практически ничего не происходит». Решение — слияние кернелов (kernel fusion): пять программ можно объединить в одну, чтобы не гонять данные в глобальную память и обратно между шагами; подробный разбор лектор анонсирует на следующее занятие. Один из студентов интуитивно предположил, что слияние может происходить прямо внутри предыдущего матричного умножения (пока данные ещё в регистрах) — лектор подтвердил, что мысль движется в верном направлении, но подробности — тоже позже.

Раздел 3. Вопросы для подготовки к защите лабораторных (теория)

Формат ответа: сначала тезис (1–2 предложения), затем аргументация от первого лица со ссылками на слайды и таймкоды — для самопроверки.

1. Почему GPU проектируют не для минимизации задержки одной операции, а для максимизации пропускной способности?

Тезис: CPU и GPU решают разные задачи — CPU старается как можно быстрее довести до конца одну последовательность операций, а GPU нацелен на то, чтобы обработать как можно больше независимых операций за единицу времени.

Аргументация: если элементы вычисления независимы (как элементы результата матричного умножения), выигрыш от их одновременной, а не последовательной обработки перевешивает возможную более высокую скорость одного ядра CPU (сл. 3–5). Именно поэтому у GPU гораздо больше простых вычислительных блоков и гораздо меньше «управляющей» логики на блок, чем у CPU (сл. 6, запись 03:39–06:01).

2. Всегда ли условное ветвление в GPU-коде вызывает расхождение варпа? Разберите на примере ReLU.

Тезис: нет, не всегда — расхождение возникает только тогда, когда ветки реально выполняют разные инструкции, а не когда они просто по-разному называются в коде.

Аргументация: код if (x>0) out=x; else out=0; расхождение вызывает — ветки выполняют разные инструкции (одна включает чтение из памяти, другая нет). А тернарный вариант out = x>0 ? x : 0 компилируется в одну предикатную инструкцию и расхождения не вызывает; логические операции (or/and/xor) тоже расхождения не создают. Именно на первом, неудачном примере лектор сам себя поправил после занятия (§4.1, запись 1:07:52–1:13:24) — общий совет курса остаётся «по возможности избегать if в GPU-коде».

3. Почему регистровая память обязательна к использованию, а разделяемая (SMEM) — нет?

Тезис: все арифметические операции физически выполняются только над данными в регистрах, тогда как SMEM — это лишь необязательный дополнительный кэш, который разработчик наполняет сам.

Аргументация: чтобы что-то сложить или умножить, значения сначала обязаны попасть в регистры — из GMEM их можно читать и напрямую, минуя SMEM (сл. 26–27, запись 24:46–29:06). SMEM полезна, когда данные из GMEM переиспользуются много раз (как в GEMM), но использовать её не обязано ни одно вычисление.

4. Почему хранение матрицы весов в транспонированном виде ускоряет обращение к памяти при матричном умножении?

Тезис: это превращает обращение по столбцам (разбросанное по памяти) в обращение по строкам (последовательное), которое GPU может объединить в меньшее число транзакций.

Аргументация: если матрица $W$ хранится в обычном (row-major) виде, чтение столбца требует прыгать по памяти на большие расстояния между соседними элементами столбца — доступ не согласован. Если же хранить $W^T$, тот же столбец становится строкой $W^T$ и читается последовательно — доступ согласован (сл. 29–32, запись 31:32–42:14).

5. Почему высокая occupancy не гарантирует хорошую производительность программы?

Тезис: occupancy показывает лишь долю занятых ресурсов SM, но ничего не говорит о том, чем именно эти ресурсы заняты и упирается ли программа в память.

Аргументация: программа с наивным матричным умножением может показывать высокую occupancy просто потому, что почти не использует SMEM и регистры (а значит, помещается много активных варпов), — но при этом останется сильно memory-bound из-за низкой арифметической интенсивности (сл. 41 и разбор GEMM, сл. 46–48).

6. Чем арифметическая интенсивность отличается от throughput (FLOP/s), и почему сама по себе AI не оценивает максимальную производительность?

Тезис: AI — это характеристика самой программы (сколько вычислений приходится на байт перемещённых данных), а не результат её выполнения; она лишь подсказывает, в какую сторону выгодно оптимизировать, а верхнюю границу реальной производительности даёт уже roofline-модель.

Аргументация: $\text{AI}=\text{FLOPs}/(R+W)$ (сл. 38) не содержит ни пиковый FLOP/s устройства, ни пропускную способность его памяти — эти две величины подставляются уже в формулу roofline $\text{Performance}\le\min(\text{AI}\cdot\text{BW},\,\text{PeakFLOP/s})$ (сл. 39, запись 50:15–1:00:01).

7. Почему наивная реализация GEMM имеет арифметическую интенсивность около 0,25 независимо от размера матрицы, а не растёт вместе с размерностью?

Тезис: и число операций чтения/записи, и число FLOPs в наивном GEMM растут линейно с размерностью $D$ по одному и тому же закону ($\approx 2D$), поэтому их отношение при росте $D$ сходится к постоянному числу, а не растёт.

Аргументация: reads$=2D$, writes$=1$, FLOPs$=2D-1$; $\text{AI}=(2D-1)/(4(2D+1))\to 1/4$ при $D\to\infty$ — уже при $D=128$ отличие от $0{,}25$ меньше процента (проверено в песочнице, §4.4). После блочной оптимизации (кэширование в SMEM, тема следующего занятия) AI можно поднять до ~240, переведя GEMM в compute-bound режим — в этом и есть смысл оптимизации (сл. 46–48, запись 1:29:06–1:41:36).

8. Почему LayerNorm в наивной реализации может занимать больше половины времени обучения, хотя вычислений там немного?

Тезис: наивный LayerNorm — это цепочка из пяти отдельных memory-bound операций подряд, каждая из которых читает данные из глобальной памяти и сразу же кладёт результат обратно, вместо того чтобы посчитать всё за один проход.

Аргументация: редукция среднего → редукция дисперсии → вычитание/деление → умножение на $\gamma$ → сложение с $\beta$ — пять кернелов, и в каждом накладные расходы обращения к GMEM доминируют над самой арифметикой (сл. 49, запись 1:43:08–1:51:53, с прямой отсылкой лектора к профилированию модели из ЛР2).

9. Почему тензорные ядра не могут заменить собой все CUDA-ядра на GPU?

Тезис: тензорные ядра — узкоспециализированные блоки только для матричных умножений небольшого фиксированного размера, а не универсальные арифметико-логические устройства.

Аргументация: на GPU тензорных ядер значительно меньше, чем CUDA-ядер (обычно 1–4 против, например, 128 CUDA-ядер FP32 на один SM), и они не предназначены для скалярной арифметики, сравнений или логических операций — этим по-прежнему занимаются CUDA-ядра (сл. 12–13, запись 10:57–13:27).

10. Что, помимо архитектурного предела (32/48/64 варпа на SM), может ограничивать реальное число активных варпов?

Тезис: чаще всего ограничивающий ресурс — нехватка регистровой памяти (реже — разделяемой памяти) на большое число одновременно активных варпов.

Аргументация: если программа расходует слишком много регистров на поток, на SM физически поместится меньше варпов, чем допускает архитектурный максимум, — либо (при явном лимите на компиляции) программа вовсе откажется запускаться (сл. 15, 41; запись 13:27–17:19 и 1:00:01–1:05:29).

11. Почему функцию потерь (loss) обязательно нужно вычислять как редукцию прямо на GPU, а не на CPU?

Тезис: loss — это по определению отображение многомерного выхода сети в один скаляр (без этого нельзя задать отношение порядка «меньше/больше» для градиентного спуска), а перенос данных на хост ради этого вычисления был бы слишком медленным.

Аргументация: выход нейросети — тензор, а не скаляр, и сравнивать «лучше/хуже» можно только одно число; значит, необходима редукция (среднее, сумма квадратов и т. п.). Поскольку данные и так лежат на устройстве, а копирование на хост медленное, редукцию выполняют прямо на GPU, а значит, разработчику нужно уметь её реализовывать эффективно (сл. 44, запись 1:21:38–1:26:32).

4.5. Скелет решения ЛР (исполнен в песочнице без ошибок)

"""
Проверка числовых утверждений Лекции 3 (роофлайн / арифметическая интенсивность / occupancy).
Не привязано к конкретной лабораторной работе курса напрямую (см. §4.4 конспекта) — но именно
эти вычисления нужны, чтобы понять, memory-bound или compute-bound операция внимания в ЛР3
(Triton Flash Attention), и стоит ли вообще её оптимизировать по этому направлению.
Библиотеки: только numpy (torch не установился в песочнице — не хватило места на диске).
"""
import numpy as np

FP32_BYTES = 4


def arithmetic_intensity(flops: float, bytes_moved: float) -> float:
    """AI = FLOPs / (R + W), см. сл. 38."""
    return flops / bytes_moved


def roofline_performance(ai: float, mem_bandwidth: float, peak_flops: float) -> float:
    """Performance <= min(AI * bandwidth, peak_flops), см. сл. 39."""
    return min(ai * mem_bandwidth, peak_flops)


def occupancy(w_active: float, w_max: float) -> float:
    """Occupancy = W_active / W_max, см. сл. 41."""
    return w_active / w_max


# --- 1. Поэлементное сложение c_i = a_i + b_i (§4.1, запись [1:13:24-1:21:38]) ---
flops_add = 1
bytes_add = (2 + 1) * FP32_BYTES  # 2 чтения (a_i, b_i) + 1 запись (c_i)
ai_add = arithmetic_intensity(flops_add, bytes_add)
print(f"[4.1] Поэлементное сложение: AI = {flops_add}/{bytes_add} = {ai_add:.4f}  (лектор: 1/12 = {1/12:.4f})")
assert abs(ai_add - 1 / 12) < 1e-9

# --- 2. Наивный GEMM: конкретный пример 7x7 из записи (§4.4, [1:29:06-1:41:36]) ---
D0 = 7
reads0, writes0 = 2 * D0, 1
flops0 = 2 * D0 - 1
ai0 = arithmetic_intensity(flops0, (reads0 + writes0) * FP32_BYTES)
print(f"[4.4] Наивный GEMM D={D0}: reads={reads0} writes={writes0} flops={flops0} "
      f"bytes={(reads0+writes0)*FP32_BYTES} AI={ai0:.4f}  (лектор: 13 flops, AI~0,22)")
assert reads0 == 14 and flops0 == 13

# --- 3. Наивный GEMM: предел при росте D — проверка расхождения с 2.md ("AI = d/4") ---
print("[4.4] Наивный GEMM, зависимость AI(D) — проверка утверждения 'd/4' из письменного конспекта:")
for D in (7, 32, 128, 1024, 4096):
    reads, writes = 2 * D, 1
    flops = 2 * D - 1
    ai = arithmetic_intensity(flops, (reads + writes) * FP32_BYTES)
    print(f"    D={D:5d}: AI = {ai:.4f}   (значение 'd/4' по этой формуле было бы {D/4:.1f} — расходится)")
print(f"    предел при D -> inf: AI -> 1/4 = {0.25:.4f}  (константа, НЕ растёт с D)")

# --- 4. Roofline: до/после оптимизации GEMM, roofline A100-класса (сл. 40, запись [1:39:05-1:41:36]) ---
peak_fp32 = 30e12       # 30 TFLOP/s fp32 compute-bound (по рисунку на сл. 40)
peak_fp64 = 475.6e9     # 475.6 GFLOP/s fp64 compute-bound (по рисунку на сл. 40)
bandwidth_intersect_fp32 = peak_fp32 / 15.4   # проверка точки излома при AI=15.4 (сл. 40)
print(f"[3.5] Roofline: BW, дающая излом при AI=15.4 и потолке {peak_fp32/1e12:.0f} TFLOP/s fp32: "
      f"{bandwidth_intersect_fp32/1e9:.1f} GB/s")

perf_naive = roofline_performance(0.25, bandwidth_intersect_fp32, peak_fp32)
perf_opt = roofline_performance(240, bandwidth_intersect_fp32, peak_fp32)
print(f"[4.4] Наивный GEMM (AI=0.25): Performance <= {perf_naive/1e12:.3f} TFLOP/s -> "
      f"{'memory-bound' if perf_naive < peak_fp32 else 'compute-bound'}")
print(f"[4.4] Оптимизированный GEMM (AI=240): Performance <= {perf_opt/1e12:.1f} TFLOP/s -> "
      f"{'memory-bound' if perf_opt < peak_fp32 else 'compute-bound'}")
assert perf_naive < peak_fp32 and perf_opt >= peak_fp32 * 0.999

# --- 5. Occupancy: пример из профилировщика (сл. 41) ---
occ = occupancy(29.43, 64)
print(f"[3.6] Occupancy (MAIProf, сл. 41): {29.43}/{64} = {occ*100:.1f}%")

# --- 6. Согласованный доступ: транзакции для устного примера (§2.7, [31:32-42:14]) ---
bus_bits, cell_bits, n_cells = 256, 32, 32
bus_bytes, cell_bytes = bus_bits / 8, cell_bits / 8
cells_per_txn = bus_bytes / cell_bytes
txns_coalesced = int(np.ceil(n_cells / cells_per_txn))
print(f"[2.7] Шина {bus_bits} бит, ячейка {cell_bits} бит, {n_cells} ячеек: "
      f"согласованно = {txns_coalesced} транзакций (в записи прозвучало 2 — расхождение), "
      f"несогласованно = {n_cells} транзакций (совпадает с записью)")
assert txns_coalesced == 4
